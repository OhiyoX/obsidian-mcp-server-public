Apply a line-surgical increment to an Obsidian .base document: only the addressed lines change, so comments, unknown keys, key order, quote style, line endings and the final-newline state outside them survive byte-for-byte. An addressed line is rewritten from the new value, so bytes *inside* an addressed line are not preserved (a non-UTF-8 byte there does not survive); lines outside them keep their bytes exactly, even bytes that are not valid UTF-8. A document holding bytes that are not valid UTF-8 supports in-place replacements and appends at the end of the document, where every existing line keeps its bytes exactly; a structural edit that cannot be mapped back byte-for-byte — inserting a line in the middle, or deleting any line — fails closed with `base-not-patchable`, because line identity is not recoverable from a lossy decode — use `write_base` for that. `ifMatch` is mandatory (the `revision` from `get_base`): a missing precondition fails with `precondition-required`, a stale one with `revision-conflict`, and in both cases the document is left untouched. Only the desktop write whitelist is addressable (view options, `formulas.<name>`, `properties.<name>.displayName`); anything else fails closed with `base-not-patchable` / `base-unknown-key`. The response always carries `warnings`: a non-empty array means `query_base` cannot serve the patched document (this server's query subset is narrower than the write whitelist), so do not assume the patch is queryable without reading it. `mutationId` is accepted for parity with the Web PATCH face and is not used as an idempotency key here — the CAS revision is the concurrency guard. Use `write_base` only when the whole document should be re-serialised.
