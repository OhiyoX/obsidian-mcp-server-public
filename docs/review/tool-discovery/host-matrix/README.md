# Phase 0 host defer/tool-search capability matrix

Status: **candidate** (branch artifact, baselines main `c860abae342a9b4ea45949de8f24690a92ec7eab`).
Scope: characterization only. This directory changes no runtime behavior, tool registration,
capability advertisement, Scope mapping, configuration, or Vault code.

## Why this exists

Wave 1 froze the eager Obsidian MCP catalog (`docs/review/tool-discovery/inventory.md`,
`eager-baseline.md`). Phase 1+ would introduce progressive discovery, but the payoff depends
on the **host**: some MCP clients can defer tool schemas or search for tools, most cannot.
This matrix records, for each MCP-client host that is actually installed on the probe machine,
what is provable about:

1. whether it has a real defer / tool-search mechanism;
2. whether it auto-loads the full tool schemas on connect;
3. whether it refreshes its tool list on `notifications/tools/list_changed`;
4. what its cross-session discovery behavior is.

The central rule: **a host is never marked supported without evidence.** Anything that was not
observed or found in an installed artifact stays `unknown`.

## Files

- `host-matrix.json` — machine-readable matrix (rendered by the probe script).
- `host-matrix.md` — rendered table (same data, human-readable).
- `evidence.md` — evidence ledger and raw probe notes.
- `phase3-host-runtime-evidence.{json,md}` — bounded Phase 3 host run (see addendum below).
- `controlled-matrix.{json,md}` — Phase 3-B controlled repeated matrix (see addendum below).
- `README.md` — this document.

The JSON and Markdown are generated by `app/scripts/probe-host-tool-discovery.mjs`; do not edit
them by hand. Edit the authored data in the script, then `--write` and `--check`.

The generated matrix also carries a `runtimeSessions` registry: actual sessions driven or
observed while the matrix was built. Each observed field is either a recorded value or `null`
(not observed); `null` is never inferred from documentation or from a static marker. The registry
is additive to schema `1.1.0` and is listed with `--session-list`.

## Classification vocabulary

Tool discovery (`toolDiscoveryMode`):

| Value | Meaning |
| --- | --- |
| `real` | A defer / tool-search mechanism exists in the installed host (artifact-declared or observed). |
| `documented-only` | A mechanism is claimed only by external documentation, with no local implementation artifact. |
| `eager-fallback` | The inspected host loads the full catalog and no defer/search path was found. |
| `unknown` | Cannot be classified from available evidence. |

Native schema auto-load: `eager-auto`, `deferred-capable`, `deferred-default`, `unknown`.
List refresh: `implemented`, `declared-only`, `not-detected`, `unknown`.
Cross-session: `re-discovered-per-session`, `cached-across-sessions`, `unknown`.

Evidence tiers (`tier`):

| Tier | Meaning |
| --- | --- |
| `runtime-observed` | Observed directly while the host was running against an MCP surface in this task. |
| `artifact-declared` | Found in an installed host artifact (binary strings, bundled source, CLI output, shipped docs). |
| `documentation-only` | Claimed only by external documentation; no local implementation artifact. |
| `not-detected` | Inspected the installed artifact and did not find the mechanism; absence is not proof of absence. |
| `not-available` | Host binary was not found locally; no capability claim is made. |
| `unknown` | Not measured. |

`validateMatrix()` enforces these honesty rules, including: a `real` cell requires an
`artifact-declared`/`runtime-observed` tier and at least one evidence id; a `documented-only`
cell requires the `documentation-only` tier; every `unknown`/`not-detected` cell must carry a
reason; and every cell's tier must be justified by a matching **evidence kind** (`runtime-observed`
needs a `runtime-observed`/`runtime-session` record, `artifact-declared`/`not-detected` need an
`installed-artifact`/`command-output` record). A `runtime-observed` cell may also cite static
supporting evidence, but a purely static finding can never be promoted to a runtime claim.
The focused test `app/test/host-tool-discovery-probe.test.js` asserts that a fabricated
`real` claim without evidence, a mismatched tier/evidence kind, and a tampered static count are
all rejected.

### What `--check` does and does not prove

`--check` recomputes a SHA-256 digest over each recorded static marker scan and fails if the
counts no longer match their digest. It does **not** re-read the installed host artifacts. To
re-derive counts from a live artifact, run `--scan <scanId>=<path>` on the machine that has it.
A scan that declares a `collection` (Gemini CLI ships its MCP code across `bundle/chunk-*.js`)
takes a **directory**: `--scan` matches the glob, sorts and dedupes the files, and aggregates
their counts into the same digest-bound record. Single-file scans keep taking one path.
Runtime-session and command-output observations that cannot be reproduced in CI are marked
`external-attestation`; `--check` never claims to have verified them. Only the Obsidian MCP
server `tools.listChanged` claim is marked `repository-test`, because an in-process handshake
in the test suite reproduces it.

## Method

Installed hosts were detected from the local machine and each one's shipped artifacts were
inspected read-only:

- **Pi** — installed package docs (`docs/extensions.md#dynamic-tool-loading`), the pi-ai provider
  serialization, the changelog, and the user's `obsidian-mcp` bridge extension; plus this
  session's own tool payload.
- **Codex CLI** — `codex features list`, `codex mcp add --help`, and marker strings in the
  installed `codex.exe`.
- **Gemini CLI** — marker strings aggregated over the `@google/gemini-cli/bundle/chunk-*.js`
  collection, plus shipped docs from the same bundle.
- **OpenCode** — marker strings in the 1.18.25 binary (provider tool-search and MCP client
  list-changed settings).
- **Cursor / VS Code** — marker strings in the workbench bundle, including the settings schema.
- **WorkBuddy** — marker strings in `resources/app.asar` (tool registry and MCP sanitizer).
- **Obsidian MCP server** — the SDK capability payload (`tools.listChanged: true`), verified with
  a local in-process probe; catalog size from the Wave 1 inventory.

Marker scans count occurrences of specific tokens (`tool_search`, `defer_loading`,
`notifications/tools/list_changed`, …) and inspect surrounding code. They are evidence of a
mechanism's presence, not proof that it is enabled for a given MCP server at runtime.

Two distinctions matter:

- **Host capability vs current integration.** Pi's host supports real dynamic tool loading
  (`pi.setActiveTools()` loader pattern) and provider-native deferred loading, but the installed
  `obsidian-mcp` bridge registers all 85 tools eagerly and installs no list-changed handler. The
  `toolDiscoveryMode` cell records the host capability; `nativeSchemaAutoLoad` records what this
  session actually observed. The same capability/integration split applies to Codex, OpenCode,
  VS Code, and WorkBuddy, whose deferral is provider- or Copilot-scoped and was not exercised
  against this Obsidian server.
- **`real` is not `enabled`.** Every `real` cell is `artifact-declared`: the mechanism exists in
  the installed build. No host except Pi was driven end-to-end, so no host is marked
  `runtime-observed` for deferral.

The `documented-only` bucket is empty in this snapshot because no external vendor documentation
was consulted for hosts that are not installed. Not-installed hosts
(`claude-code`, `claude-desktop`, `windsurf`, `aider`, `zed`, `goose`, `openclaw`, `hermes`) are
listed separately with no capability claim.

## Server baseline

The Obsidian MCP server advertises `tools.listChanged: true` (SDK 1.30.0) and registers all **86**
tools unconditionally (the frozen Phase 0 snapshot above recorded 85; `get_note_context` was added
in #111); `tools/list` is not filtered by Scope, Vault allowlist, or read-only mode.
Scope is enforced per `tools/call`. List refresh is only useful if a host handles the notification,
and host visibility is never authorization.

## Reproduce

```sh
cd app
node scripts/probe-host-tool-discovery.mjs --check      # validate + digest + drift check (default)
node scripts/probe-host-tool-discovery.mjs --json       # matrix as JSON
node scripts/probe-host-tool-discovery.mjs --markdown   # rendered table
node scripts/probe-host-tool-discovery.mjs --scan-list  # list scan ids, artifacts, and collection globs
node scripts/probe-host-tool-discovery.mjs --session-list  # list runtime session observations (null = not observed)
node scripts/probe-host-tool-discovery.mjs --scan cursor-workbench-3.21.16=/path/to/bundle.js
node scripts/probe-host-tool-discovery.mjs --scan gemini-cli-bundle-0.57.0=/path/to/gemini-cli/bundle
node scripts/probe-host-tool-discovery.mjs --detect     # read-only local host detection (best effort)
node scripts/probe-host-tool-discovery.mjs --write      # regenerate the checked-in JSON + Markdown
```

`--scan` reads one local artifact, or one collection directory when the scan id declares a
glob source, and re-runs the recorded token recipe, reporting per-token mismatches. A
collection scan enumerates the directory, keeps only files matching the declared pattern in
stable sorted order, dedupes duplicate directory entries, and aggregates their counts. It is
the only way to re-derive the counts; `--check` alone verifies the digest of the recorded
numbers. `--detect` is intentionally not part of `--check`: host detection depends
on the machine and launch shim, so it cannot be a deterministic gate. On this machine `codex`
reports `0.151.0` through the bash shim and a different pre-release through the Windows `.cmd`
shim; the matrix records the version whose installed artifact was actually scanned.

## Phase 3 addendum: Pi host bridge driven end-to-end (candidate)

`phase3-host-runtime-evidence.{json,md}` records a bounded host run of the real Pi host through the
user's custom eager bridge extension against an isolated loopback scratch Obsidian MCP server. It
was recorded against the 86-tool catalog at branch base `9a99a5a` (the frozen Phase 0 snapshot above
recorded 85).

- real Pi 0.99.2 host, requested provider/model `opencode-go/deepseek-v4.1-flash` (the configured
  `--provider`/`--model` alias, not provider-attested identity). The scratch API key is generated in
  memory (`crypto.randomBytes`) and passed to children only through `spawn` `env` — never in argv, a
  shell string, a fixture, a temp file, stdout, or stderr.
- The Pi bridge is the user's **custom extension** (`obsidian-mcp/index.ts`), which eagerly
  `registerTool`s every MCP tool. This is not provider-native deferred loading, and no host
  defer/search mechanism is claimed; native Pi auto-defer stays `unknown`.
- `full` advertised **86** tools (51 read-only; 142,841 serialized `tools/list` array bytes, i.e.
  142,754 summed per-descriptor bytes plus `count + 1` = 87 framing bytes), `core` advertised **6**,
  and `info,search,context` advertised **7**. Within the recorded snapshot that framing relation is
  exact, so the byte total is not schema drift. (A later main change, #117, widened six plan
  `maxDiffChars` minimums, so a fresh catalog on current main sums to 142,736 descriptor bytes /
  142,823 array bytes; that 18-byte delta is a documented schema widening, not framing drift.)
  `full` and `core` shared one prompt while `module` used a different prompt, so this is a bounded
  characterization, not a controlled cross-profile comparison. All three nested Pi runs settled,
  exactly matched the fixture answer, and called only `readOnlyHint:true` tools.
- The scratch server ran `OBSIDIAN_READ_ONLY=true`. That flag is **not** a blanket execution gate
  (`manage_publish` still writes scratch `DATA_PATH` publish state and `reindex_vault` still queues).
  What was actually observed: a direct `write_note` probe was denied and created no file, and the
  per-run guard is a post-hoc `readOnlyHint` assertion, not an execution gate.

Reproduce: `cd app && node scripts/host-bridge-evidence.mjs`. The matrix's
`runtimeSessions` registry is intentionally not regenerated from this run, so the
cells above remain the Phase 0 snapshot.

## Phase 3-B addendum: controlled repeated eager-bridge matrix (candidate)

`controlled-matrix.{json,md}` extends the Phase 3 addendum into a controlled, repeated,
same-prompt matrix. Six deterministic read-only anchor tasks are drawn from the frozen
50-task fixtures (`app/test/fixtures/tool-discovery-eager-tasks.json`) and repeated five
times under three runtime operator profiles. For one task every profile uses the
byte-identical prompt/fixture/expectation under **equivalent auth conditions**: each trial
runs on a fresh isolated loopback server with a fresh single-use ephemeral all-scope key,
so the granted principal is controlled while the auth key *bytes* differ per trial. Only the
runtime operator profile differs.

| profile | operator profile | visible tools (per snapshot) |
| --- | --- | --- |
| `full` | `full` | 86 |
| `core` | `core` | 6 |
| `oracle-module` | `custom` (exactly `expectedTools ∪ alternativeTools`) | 2–4 per task |

The per-task `oracle-module` is an **oracle upper bound**, not deployable autonomous
discovery. The trial order is pre-registered and balanced (`schedule.sha256`), each trial
uses a fresh temp Vault/DATA/port/ephemeral in-memory key, and the real installed Pi
0.99.2 host is driven through the custom eager bridge with
`--no-session --no-context-files --no-skills --no-prompt-templates --no-extensions -e bridge -nbt`.

Result: **90/90 trials executed, 70 success, 0 infrastructure errors, status complete**.

| task | core coverage | full | core | oracle-module |
| --- | --- | --- | --- | --- |
| `note-read-full-en` | positive | 5/5 | 5/5 | 5/5 |
| `search-relevance-en` | positive | 5/5 | 5/5 | 5/5 |
| `server-info-capability-mixed` | partial | 5/5 | 0/5 | 5/5 |
| `links-backlinks-en` | missing | 5/5 | 0/5 | 5/5 |
| `files-read-zh` | missing | 5/5 | 0/5 | 5/5 |
| `compare-versions-zh` | missing | 5/5 | 0/5 | 5/5 |

A success is an exact normalized fixture answer AND at least one **actually executed**
MCP call in `expectedTools ∪ alternativeTools`; an unrelated call cannot stand in.
**Boundary:** evidence bearing is a proxy — a call is accepted by tool-class membership
(`expectedTools ∪ alternativeTools`) plus non-error status; the harness does **not** assert
that the result payload actually contains the answer, so a success here is not a claim of
observed payload causality for general tasks. The per-cell diagnostics are deliberately
labelled: `answerMatches` counts every usable trial whose answer matched exactly, while the
honest `answerOnly` counts exact-answer trials with **no** declared evidence call (so
`links-backlinks-en/core` is `answerMatches:5, answerOnly:5`, and
`server-info-capability-mixed/core` is `answerMatches:0, evidenceOnly:5`).
`full` and `oracle-module` hold every one of the 30 cells; `core` holds the two
positive-coverage tasks and fails the partial/missing-coverage tasks exactly as
pre-registered. Notably, `links-backlinks-en/core` produced the correct path with
`search_notes`/`get_note` but no declared evidence call, so it is an observed task
failure, not a success. The `server-info-capability-mixed/core` cell is the partial
case: `server_info` is visible but `index_status` is not, so the retrieval embedding
model cannot be reported.

Control gate: no mutating/non-readOnly host call in the batch, no sentinel leak, and the
direct `write_note` probe was denied and created no file. The missing-tool sentinel lives
only in the scratch vault copy of `Attachments/diagram.svg`; the artifact stores only its
`sha256`/length, and the missing-tool `core` profile never returned it. Catalog byte
totals are per-snapshot and compare `full` 142,823 array bytes / 142,736 descriptor bytes
vs `core` 15,117 / 15,110. The per-task oracle snapshot varies by task (2–4 tools) and is
recorded per trial in `controlled-matrix.json` (the aggregate `costMetrics` row is the
last oracle snapshot). Provider
request-payload tokens were not measured (`UNMEASURED`); `ceil(bytes/4)` is a coarse
estimate, not a tokenizer result. The reduced-scope host negative was not fabricable (the
configured-env key grants all MCP scopes and the installed bridge sends only `X-API-Key`),
so in this batch it is recorded `blocked`, not fabricated. A dedicated isolated
OAuth-managed-key scope submatrix was added afterwards and is recorded separately in
`scope-matrix.{json,md}`; it does not change any success count in this 90-trial artifact.

Reproduce: `cd app && node scripts/host-controlled-matrix.mjs` (bounded wall time,
resume-safe with `--resume`); verify the committed artifact with
`node scripts/host-controlled-matrix.mjs --verify`.

## Phase 3-B scope addendum: isolated OAuth-managed-key host submatrix

`scope-matrix.{json,md}` is a separate, bounded experiment that closes the reduced-scope
host gap without touching the 90-trial controlled matrix. It uses the existing
`createOAuthService()` provider to seed managed API keys into a fresh isolated `DATA_PATH`
(only the provider's hashed record is persisted; the secret lives in memory and is injected
per Pi child through `OBSIDIAN_MCP_API_KEY`), then drives the real installed Pi 0.99.2 host
through the eager bridge against that loopback server. It reuses the byte-identical
`files-read-zh` prompt/profile/fixture and a fresh random attachment sentinel of its own.

- `files-allowed` (scopes `obsidian.read` + `obsidian.files`): the file tool is advertised and
the sentinel is returned with an actually executed `get_file`/`pull_file` call.
- `files-missing-scope` (scope `obsidian.read` only): the server's scoped `tools/list` drops
the file tools and the bridge announces only the filtered catalog, so the sentinel is never
returned and no unauthorized file tool is advertised.
- `invalid-credential`: the bridge attempt reaches the loopback server and is rejected `401`.
- `missing-env-key`: the bridge hard-throws at extension load, so the server is never reached
(a host init failure, not a server `401`).
- `zeroScope`: `createApiKey([])` normalizes to all scopes (`normalizeScopes` fallback), so a
true zero-scope managed key is unconstructible and is recorded `blocked`; it is never faked
as a PASS and never replaced with an invalid credential.

An optional direct `tools/call` assertion is labelled **transport-only**; it is not host
evidence.

- No host had been driven through an end-to-end agent task before the Phase 3 addendum. Phase 3
  drove the real Pi host end-to-end through the user's custom eager bridge extension (not native
  provider deferral); no other host was driven end-to-end.
- No host's native runtime tool-list/deferral behavior against a live MCP server was exercised; the
  Phase 3 Pi run used an eager custom bridge, so native Pi deferral stays `unknown`.
- Codex, OpenCode, and Gemini were observed only at the configuration/connection layer; no tool
  count or deferral state was visible from their CLIs.
- Cross-session persistence was not measured for any host.
- Marker-string absence (Cursor) is not proof the host always loads eagerly.
- Static marker counts are digest-checked by `--check` but not re-derived unless `--scan` is run
  against the artifact on the probe machine; for the Gemini collection that means the bundle
  directory, not a single `chunk-*.js` path.
- `pi-session-observation` (this session) and the `command-output` records are external
  attestations: they are recorded honestly and never claimed as `--check`-verified.
- Byte/token cost of the eager catalog and tool-selection accuracy remain measured only in Wave 1.
- This is a **candidate** branch artifact. It says nothing about merge, release, or production.

The Phase 3 addendum is a first host acceptance step: it drives the real Pi host end-to-end against
an isolated live MCP server and records the 86-tool list delivered to the model. Because that run
used the custom eager bridge (not the host's native provider deferral), no deferral/tool-search cell
moves from `artifact-declared` to `runtime-observed`; native Pi deferral stays `unknown`, and every
unmeasured field stays `unknown`. The remaining next action is to drive a host whose native deferral
can actually be observed end-to-end, and to record the tool list delivered in that mode.
